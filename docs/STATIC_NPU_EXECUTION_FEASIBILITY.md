# Static NPU execution feasibility — Phase 9

**Decision (2026-10-27): NO-GO as a new exact Top-K research contribution.** The tested graph is a useful NPU systems optimization, but the two-level selection structure is established prior art, and physical FP16-subnormal behavior prevents a total exactness guarantee over finite FP16 scores. This decision does not alter the Phase 7 or Phase 8 conclusions. No manuscript or confirmatory study was started.

## Scope, environment, and evidence boundary

The feasibility question was whether a fixed-shape OpenVINO graph could perform tile and final Top-K on the physical consumer NPU in one inference request, replacing host-controlled tile batches and merges. The test machine is the Core Ultra 7 255H / Intel AI Boost 3720 with OpenVINO 2026.4.1, NPU driver 1004512, compiler 458778, and an RTX 5060 Laptop GPU. The recorded environment is `results/doctor.json`. All new raw observations are under `results/phase9/`. The source base before Phase 9 was Git `8c705ee73aa7c1ec3b4543292625f82e5cdd9b30`; the Phase 9 source revision and file hashes are recorded in `results/phase9/manifest.json`.

All timing uses host-resident FP16 score input and host-resident stable Top-K index output. Compilation and the first inference are excluded from steady-state timing. We used development query 0 from the existing SIFT1M, SciFact, and FiQA score files; prior evaluation and confirmatory holdouts were not accessed. Their provenance, score transforms, and FP16 conversion remain documented in the respective Phase 5 dataset manifests. The new measurements are exploratory observations within one process, **not independent experimental sessions**. Reported P95 values from three or five runs are only descriptive and cannot support inferential claims.

## Mechanism and execution structure

For `N` scores, tile width `W=256`, and `M=ceil(N/W)`, the prototype pads the final tile with `-∞` and compiles one static `[M,W]` FP16 graph. The graph computes Top-K within each tile, adds each tile's global index offset, reshapes the `MK` candidates, and performs a second Top-K over candidates. It returns only `K` values and `K` global IDs. `StaticNPUTopK` compiles **explicitly** for `NPU` with `NPU_COMPILER_TYPE=PLUGIN`, checks `EXECUTION_DEVICES == ["NPU"]`, and calls one synchronous `InferRequest.infer` per query. The NPU plugin's implementation states that inference work is offloaded to the NPU, though the measured synchronous call also includes runtime submission and data movement; no per-operation hardware timing was inferred from it. [OpenVINO NPU plugin](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_npu/README.md), [NPU device documentation](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/npu-device.html).

The host still pads input, submits and synchronizes once, copies 6K software-visible output bytes (`K` FP16 values and `K` int32 IDs), sorts K candidates by score descending/index ascending, and scans the original input to certify the selected boundary. Thus this is a **hybrid** implementation. The output-byte figure is the returned tensor size, not a measured physical bus transfer. The current 3720/driver configuration is below OpenVINO's documented NPU40XX/driver-4621 bounded-dynamic-shape preview requirement, so static input shape is appropriate. A generic operator support list was not treated as proof that this particular graph compiles or runs. [OpenVINO NPU shape limits](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/npu-device.html).

The legacy fixed and adaptive paths submit batches of local Top-K results, synchronize to inspect them, and merge/certify on the host. At N=1,000,000, K=10, W=256, batch=8, they made **489** device submissions on the measured SIFT development query. The static graph made **one**. Direct native NPU Top-K also made **one**; any advantage over direct Top-K cannot be attributed to fewer host/device boundaries. It plausibly comes from dividing a very long Top-K input into shorter local selections and a smaller final selection, but the experiment did not isolate internal compiler kernels or establish a device-only cost model.

An abstract cost expression is `M·C_topk(W,K) + C_topk(MK,K) + O(N)` for input preparation and host rank certification, plus one runtime submission. This is a structural expression, not a measured NPU operation count or proven asymptotic bound on OpenVINO's opaque Top-K implementation. The `MK` final candidate count also predicts a performance loss as K grows; the K=100 observation below is consistent with that prediction, not proof of the compiler's internal cause.

## Exactness argument and numerical limit

Define the total order by `(score descending, global index ascending)`. If every local Top-K is exact under this order, the global Top-K is contained in the union of the local K sets: each omitted element has at least K elements in its own tile ranked above it. A final exact Top-K over that union therefore gives the global answer. This is the standard hierarchical Top-K lemma and supplies no new algorithmic theorem.

OpenVINO's Top-K tie behavior and FP16 numerical semantics cannot be assumed to meet that lemma. The prototype therefore uses `certify_rank` on the host. It checks that the returned K IDs are distinct and in range and that their NPU values equal the source FP16 values. After stable sorting, let the last chosen pair be `(τ,j)`. It counts all source scores greater than `τ`, plus scores equal to `τ` at indices less than `j`. If this count equals K−1, exactly K−1 source pairs outrank the last chosen pair. Since the K distinct chosen pairs are all at least as high as that pair, they must be the exact stable Top-K. This proves **soundness of every successful return for any finite FP16 input**; it does not prove that the NPU will return a certifiable set. On failure the API raises `StaticGraphMismatch`, with no CPU substitution or returned wrong answer. The certificate is an O(N) host scan and is included in end-to-end timing.

The physical NPU reproduced the decisive earlier counterexample: a 64-value positive/negative FP16-subnormal ramp embedded in a 512-value vector at K=4 produced a returned boundary of rank **64**, not rank 4. The new certificate rejected it; see `results/phase9/static_graph_edge_cases.json`. Five other edge probes passed: a normal one-ULP sequence, all equal scores, signed zero, a boundary tie, and an irregular N=257 case with one padded score-bearing tile. These samples do not establish total exactness over all non-subnormal FP16 vectors. The supported **safety contract** is “exact stable indices or explicit failure” for finite FP16 input with N>W and 1≤K≤W. A total exact-selection contract over the full finite FP16 domain is **not established**. FP32 is not supported by this graph.

Subnormal inputs are not rare by mere presence: the measured development score files contained 0/1,000,000 such scores for SIFT1M query 0, 3/5,183 for SciFact query 0, and 35/57,638 for FiQA query 0. All three whole-vector results passed the rank certificate. Three queries cannot estimate a dataset-wide failure frequency or justify ignoring the counterexample.

The following are medians in milliseconds from the Phase 9 raw JSON files. Every listed method matched the independent exact reference on these inputs. `Static` includes host padding, one synchronous NPU call, output copy, stable sorting, and the full rank certificate. The CPU and CUDA methods use the same host-input/host-output contract; CUDA's corrected tie-repair implementation is the current repository version, including any repair overhead when triggered. No historical Phase 7 speedup is used here.

At SIFT1M N=1,000,000, K=10, the static graph was 5.25× faster than direct NPU in this one-process pilot and 9.56× faster than the submission-aware NPU method, but 1.35× slower than C++ CPU and 6.92× slower than CUDA. Its median synchronous infer interval was 21.816 ms and median host rank certificate 4.237 ms; median padding was 0.546 ms. The medians of individual components need not sum to the median end-to-end value. Its requested input tensor was 2,000,384 bytes and output tensors totalled 60 bytes. The submission-aware path reported 489 calls and 46,944 output tensor bytes. These are software-visible counts, not measured bus traffic.

The advantage weakens as K grows on that same SIFT query: at K=1 the static/direct medians were 5.992/148.273 ms; at K=100 they were 121.306/139.025 ms. Stable CUDA was 2.536/2.342 ms, respectively. Changing W from 256 to 128 or 512 at K=10 worsened the static median from 27.236 ms to 45.694 or 35.433 ms in separate short runs. A synthetic N=16,385 tied-score K=10 run passed at 1.785 ms static versus 2.959 ms direct; a near-tie K=100 case passed at 3.927 versus 4.790 ms. These are development observations, not independent-session effect estimates.

Raw descriptive P95 values and all per-run timing/profiling fields remain in the corresponding `results/phase9/bench_*.json` files. For example, SIFT1M N=1,000,000 K=10 had a five-run static P95 of 30.989 ms and direct NPU P95 of 146.428 ms. Five correlated runs are insufficient for a confidence interval, stable tail estimate, or a claim of generalization. Throughput under the sequential one-query contract is simply `N / end-to-end latency` (36.7 million scores/s for that static median); no batched or concurrent throughput was measured.

## Critical prior-art comparison

| Work | Relevant mechanism | Relation to this prototype |
|---|---|---|
| [DeepSelect, author technical description](https://github.com/deepseek-ai/DeepSelect/blob/main/docs/DeepSelect-deep-dive.md) | Device-resident threshold/filter/compaction; its cluster path also computes local Top-K and a global Top-K within one GPU execution structure. | Strongest direct structural precedent for local-to-global selection without host merge. Its adaptive kernel is more sophisticated than this fixed graph. |
| [RTop-K, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/ca1b93fc0f3560ba84eb0bc8de6d8f91-Abstract-Conference.html) | GPU row-wise Top-K with binary-search-based selection. | Different primitive, but confirms extensive accelerator-side exact-selection prior art. |
| [RadiK, ICS 2024](https://doi.org/10.1145/3650200.3656596) | GPU-parallel radix Top-K. | Different primitive and hardware; a static NPU graph alone is not a new selection algorithm. |
| [Approximate Top-k for Increased Parallelism, NeurIPS 2024 workshop](https://neurips2024-enlsp.github.io/papers/paper_64.pdf) | Bucket-local selection and second-stage merge. | Related two-stage structure, but its limited per-bucket budget can make the overall method approximate; local budget K in this prototype is mathematically exact. |
| [Split-bucket partition, 2024](https://link.springer.com/article/10.1007/s11227-024-06031-x) | Integrated GPU selection stages and host-operation reduction. | Reinforces that stage integration and reduced host work are established systems themes. |
| Existing CATS-NPU fixed/adaptive/submission-aware paths | Exact conditional tile-selection theory with CPU routing/certification. | This study moves the local/global *selection work* into one compiled NPU graph, while host rank checking remains. |

The literature search found no evidence here that this exact OpenVINO graph on Intel 3720 has already been published, but absence of such a deployment report is insufficient to claim novelty. The distinguishing fact demonstrated is a **device-specific implementation and performance observation**, not a new algorithm or proof. The host rank certificate is a straightforward complete rank check, not a new exactness certificate. The current data do not establish a novel architectural model or a publishable systems result beyond known fused hierarchy.

## Independent feasibility gates and decision

| Gate | Finding |
|---|---|
| A — physical technical feasibility | **Pass.** The static graph compiled with the plugin compiler, reported `["NPU"]`, executed one infer request, and returned independently checked results on three development datasets and edge cases. |
| B — total exactness | **Fail for finite FP16.** The reproduced subnormal counterexample is rejected, so successful answers are sound, but the system cannot return exact Top-K for every legal finite FP16 input without a separate solution. A narrower empirically tested domain is not a proof of device behavior. |
| C — systems benefit | **Pass as preliminary engineering evidence.** One submission replaces 3–489 in measured hybrid cases and reduces software-visible candidate output. End-to-end latency improves against the strongest measured NPU baseline for K=10 development examples. Direct NPU already uses one submission; the static advantage over it reflects the changed selection structure. K=100 benefit is small; CPU/GPU often remain faster. |
| D — scientific novelty | **Fail for this mechanism.** Two-level local/global selection and device-side stage integration have strong prior art. The current implementation and simple rank scan do not supply a distinct algorithmic or sufficiently characterized systems contribution. |

**NO-GO** for a full confirmatory campaign or journal manuscript based on this mechanism. The short pilot falsifies neither the usefulness of reducing synchronization nor the possibility of a different NPU-native exact mechanism. It establishes that the specific fixed two-level graph is feasible and valuable as software, while failing the stated total-correctness and novelty gates. Any future research direction would need a different mechanism that handles the numerical/tie domain without silent CPU repair and a demonstrable distinction from fused hierarchical selection; it should start with a bounded physical experiment and a new protocol, not reuse the Phase 7 or Phase 8 holdouts.

## Reproduction

From the repository root in the existing virtual environment, run `python -m pytest tests/test_static_graph.py -q`, then `python scripts/check_static_graph_edges.py` and `python scripts/benchmark_static_feasibility.py --input results/phase5/sift1m/q0000_n1000000_neg_l2_f16.npy --k 10 --repeats 5 --out results/phase9/<new-name>.json`. The benchmark refuses to overwrite an existing output. The other development inputs and configurations are named in the raw `bench_*.json` files. `scripts/probe_static_npu_graph.py` preserves the earlier gap-diagnostic graph and its raw exploratory observations; `src/cats_npu/static_graph.py` is the rank-certified prototype used in the comparisons. Reproducing the performance numbers requires the physical NPU and matching compiler/runtime environment; CPU compilation alone is not execution evidence.
