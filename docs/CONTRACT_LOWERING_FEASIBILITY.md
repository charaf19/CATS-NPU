# Phase 10: contract-guided Top-K lowering feasibility

**Decision: NO-GO for the investigated RankGuard contribution. Assessed 2026-10-29.** Automated selection of the existing integer representation, guarded precision rewriting, counterexample-driven candidate rejection, and a host rank certificate do not establish the requested new mechanism. A validator of the actual compiled mapping would be a different deliverable; this project has neither implemented one nor identified a new proof technique that distinguishes it from existing translation-validation and accelerator-mapping work. Gate A fails before prototype development. Gate D also lacks an additional demonstrated capability over manual stable INT32. No new physical inference, benchmark campaign, confirmation-data access, or manuscript work was undertaken.

This is a decision about the concrete mechanisms examined here. It is not a proof that every possible rank-aware compiler is unoriginal or infeasible. One additional timing run, device probe, or installed-compiler trace would not resolve the current originality failure; a conditional GO is therefore unwarranted.

**Research problem.** For immutable finite FP16 input `x[0..N-1]`, define `i ≺x j` when `x[i]>x[j]`, or when their numerical values are equal and `i<j`. Both signed zeros belong to the same numerical class. `T_K(x)` is the first K indices in this total order. NaN and infinities are unsupported. Scores are supplied FP16 values; no claim concerns the pre-quantization FP32 retrieval ranking.

A contract-guided compiler would take a domain contract `C`, a graph `G`, and a target execution model `H`, and return a lowered graph `L` with justified obligations or explicit rejection. Total correctness requires

    for every x in C: decode(exec_H(L, encode(x))) = T_K(x).

An exact-or-reject implementation instead requires

    for every x in C: run(x) returns either T_K(x) or an explicit failure.

The second property permits rejection of a wrong device result. It supplies no lower bound on acceptance and is already provided by the existing full-input host certificate. Rejecting everything is safe but useless. A new contribution needs both a differentiated technical property and meaningful execution capability.

Four correctness levels must remain separate: (1) mathematical ordering transformation; (2) graph correctness assuming specified primitive semantics; (3) correctness of the actual compiler-produced executable relative to those semantics; (4) agreement observed on particular physical executions. The final audit establishes conditional arguments for levels 1–2 and finite evidence at level 4. It does not establish level 3 universally.

BOLT is the September 25, 2026 **preprint**, not a claim about a peer-reviewed venue or Intel NPU support. Its proof premise includes a formal hardware model. The source-backed Alive2, Alive-NJ and Diospyros descriptions show that automated checking, precondition inference and target-aware synthesis are implemented capabilities, not merely conceptual predecessors. Their scope differences are material; none is described as an existing complete exact-TopK compiler for this device. Similarly, TASO's proofs relative to operator specifications must not be promoted to proofs of arbitrary FP device execution.

The implementation inspection checked Alive-NJ's `alive/precondition/inference.py`: candidate preconditions call `check_refinement`, add returned counterexamples, and continue inference. TASO's `verify/verify.py` supplies operator axioms and asks Z3 whether source and target can differ; its axioms include addition associativity, so its proof model is not bit-exact IEEE arithmetic. Diospyros's `src/translation-validation.rkt` compares interpreted source/target outputs on shared symbolic inputs using Rosette. These are concrete precedents with explicit semantic boundaries. Their pinned file/blob identities and inspected line ranges are recorded in `results/phase10/20261029/prior_art_review.json`.

**Strongest investigated construction.** The bounded candidate was a contract-directed lowering selector: represent the finite score order, track index provenance and capacity, check modeled conversions, choose a legal static stable graph, reject unsupported cases, and validate every returned candidate set. Its obligations would include order embedding, signed-zero equality, stable boundary selection, correct tile-major ID composition, padding below valid ranks, safe integer arithmetic, supported operations, and strict NPU placement. It could reuse `score_codes`, `graph`, and `certify_rank` unchanged.

The reduction is explicit. If the available target profile preserves INT32 TopK, this construction emits the current manual stable-INT32 hierarchy. If it detects INT16-to-FP16 or lossy INT64 narrowing, a type/range guard rejects that alternative. Searching these alternatives with counterexamples is conventional synthesis; proving their guards is conventional rewrite validation. Retaining the host certificate gives exactly the same instance guarantee as the baseline. Removing it leaves the same unproved hardware-primitive assumptions. Thus the proposed automation supplies engineering convenience but no demonstrated new guarantee, accepted input domain, execution structure, or systems benefit.

An actually novel composition is not ruled out merely because its components are known. What is absent here is a new interaction property: no smaller trust base, new proof rule for target lowering, safe additional domain, lower-cost sound certification, or verified treatment of a transformation that defeats the closest equivalent technique has been demonstrated. This is why implementation was stopped at the audit, rather than building a compiler facade.

**Mathematical criterion and proof.** Restrict attention to a fixed elementwise scalar map `f` followed by an exact stable selector. Assume target comparisons form a total order on the mapped values, original order supplies the tie priority, and IDs are carried correctly. Stable Top-K is preserved for **every vector over the declared scalar domain and every valid K** if and only if

    a < b  implies  f(a) < f(b),
    a = b numerically  implies  f(a) = f(b).

Sufficiency follows because every pair's score order and equal-score index priority are unchanged. Necessity follows using two-element, K=1 witnesses: if `a<b` but `f(a)>=f(b)`, place `[a,b]`; the source winner is index 1 and the target winner is index 0. If numerically equal representations map differently, put the smaller mapped representation first; source index 0 wins the tie but target index 1 wins. This includes signed zero. This is an elementary order-embedding criterion, not a novel compiler theorem. For one fixed vector/K it is sufficient, not necessary: collisions entirely below that instance's cutoff can be harmless.

For an enumerated scalar domain sorted numerically, checking each adjacent strict inequality and equality suffices by transitivity. For FP16 this covers all 63,488 finite words and 63,487 numerical classes. It does **not** enumerate all tensor graphs, shapes, K values, indexing operations, compiler states, or context-dependent device behavior. The reduction from vectors to scalar checks assumes that the transformation really is the fixed elementwise map being checked and that the selector obeys its specified semantics. These assumptions cannot be inferred from passing scalar hardware probes.

The normalized radix code `q` already used here is `(~b)&65535` on negative finite words and `b xor 32768` otherwise, after replacing negative-zero bits with positive-zero bits. The familiar binary16 sign/exponent ordering proves the criterion. Its finite range is `[1024,64511]`. Subtracting 32768 fits the same 63,487 classes in INT16 without loss **if** integer operations retain INT16 semantics. INT32 storage also fits, and conversion of these particular codes to FP32 is exact because every code is below 2^24. None of these statements proves what an opaque compiled operation executes.

**Decisive new CPU analysis.** `scripts/audit_contract_lowering.py` enumerates the entire finite scalar domain, checks explicitly supplied conversion models, and constructs independent Python stable-order counterexamples. It adds no NPU method, compiler pass, automatic profile extraction, or synthesis engine. Its final output is [contract_audit_final.json](../results/phase10/20261029/contract_audit_final.json); the initial development audit is preserved beside it.

|---|---:|---|

| INT64-to-signed-INT32 on four boundary values | 3 of 4 | One adjacent inversion; bounded witness analysis, not exhaustive INT64 enumeration. |

For the INT16/FP16 model, scores `[-65504,-65472]` (words `0xfbff,0xfbfe`) encode as centered integers `[-31744,-31743]`; both become `-31744` in FP16. K=1 should return index 1, while stable selection of the converted codes returns index 0. For unnormalized zero codes, input `[-0,+0]` becomes `[32767,32768]` and incorrectly selects index 1. INT64 values `[2147483647,2147483648]` narrow to `[2147483647,-2147483648]`, reversing their order. These are **CPU model witnesses**, not newly executed NPU measurements.

By the pigeonhole principle, a scalar route with only 12,160 reachable comparison values cannot distinguish all 63,487 numerical FP16 classes. Merely rearranging codes within that same route cannot repair it for all vectors. This bound applies to the analyzed centered INT16-to-FP16 path, not every possible FP16 encoding, multi-key graph, or hardware implementation. In general, a single finite FP16 scalar comparison also cannot represent a strict global `(score,index)` key for N>=2: there are `63,487*N` pairs and only 63,487 finite numerical FP16 values. Stable selection with indices carried separately avoids that packing requirement, as the baseline already does. Multi-pass or lexicographic constructions remain possible and require their own analysis.

The model audit's passing assertions mean that the diagnostics produced the expected safe/unsafe classifications. They do not mean every lowering passed. Eight targeted audit tests exercise false ties, both signed-zero split orientations, exhaustive model classification, exact INT64 reference arithmetic, and invalid domains. Together with the existing encoding/graph/checker regression subset, **24 tests passed**; Ruff passed for the two new Python files. No solver-generated proof certificate or proof-assistant formalization is claimed.

**Composition, sizes, and output safety.** Under exact stable primitives, the existing local-K lemma preserves every global winner. Local equal-score candidates occur in ascending local index; tile-major flattening preserves global tie priority; final stable TopK and correct Gather recover the required IDs. For the retained graph require integer `N>W>=K>=1` and `ceil(N/W)*W<=2^31-1`. A sentinel strictly below valid codes handles irregular tails; all arithmetic, shapes and gathers must satisfy their declared semantics. Compiler rejection, unsupported operation, allocation failure, or an output-check failure is an explicit unsupported execution, rather than a CPU replacement result.

The existing host checker requires K unique valid IDs and consistent values/codes, sorts just the K proposed candidates by the contract, and counts the full-input rank of the last `(score,index)` pair. Acceptance at rank K proves that those K candidates exhaust the K correct winners. This trusts host comparisons, indexing, the immutable input, and checker execution; it is independent of correctness of the NPU selector. Sorting the proposed K candidates does not fill missing winners. The proof and measured host role already appear in the final audit. Attaching that checker to a generated graph neither validates every compiler transformation nor strengthens the baseline's exact-or-reject guarantee.

**Installed compiler and evidence boundary.** The preserved public compiler revision `c74b1265f28dc5a8f08dd50babd2a063cb59ac6e` marks FP16, FP32 and 32-bit-integer TopK inputs legal in `adjust_software_ops_precision.cpp`; its TopK converter uses FP16 for other cases. `convert_precision_to_i32.cpp` narrows signed/unsigned 64-bit integer types. Local snapshots, license, blob IDs and upstream links are in [sources.json](../results/final_research/20261028/upstream/sources.json). These rules are consistent with the recorded INT16 rounding and INT64 narrowing. The October 28 audit already reproduced those patterns; Phase 10 does not claim their rediscovery.

An input dtype, graph serialization, `EXECUTION_DEVICES=["NPU"]`, or successful compilation does not describe every internal numeric operation. A sound executable validator would require an identified installed compiler/binary and a checkable lowered representation or formally justified hardware semantics, including TopK stability and ID routing. Matching a public pass is useful evidence but not that representation. This repository has no such validated connection for the packaged compiler. A debug IR trace could narrow causal attribution; it would not by itself prove all later code generation and runtime behavior or supply a novel verification technique.

For an unrestricted black-box executable, any finite non-exhaustive test transcript is also consistent with an implementation that behaves correctly on all queried inputs and fails on one unqueried input. Thus physical tests alone cannot establish universal correctness without additional structural assumptions or exhaustive coverage of the complete executable input/state domain. This elementary indistinguishability argument does not prohibit verification of a modeled compiler or hardware; it identifies the missing premise. The familiar host certificate handles each result despite that gap and remains the available safety mechanism.

**Practical comparison and mechanism isolation.** The unchanged paired SIFT development pilot (`paired_sift_dev_q0000_n1000000_k10_with_stable.json`, N=1,000,000, K=10) measured host-input-to-host-output medians of 30.860 ms for stable INT32, 38.6571 ms for split-key, 27.1454 ms for FP16 static, 131.6917 ms for direct NPU, 20.4029 ms for C++, and 3.0193 ms for stable CUDA. Encoding, staging, inference and output checking belong to the INT32 timing. These are five repetitions per method in one interleaved process, not independent sessions; there are no Phase 10 speedups, P values, or new confidence intervals.

Emitting that same INT32 graph cannot attribute an improvement to contract-guided compilation: integer encoding and hierarchy already explain its execution. Offline legality analysis need not add per-query overhead, so this study does not invent a runtime penalty for automation. It also supplies no measured new graph or reduced verification cost. Native stable TopK already has documented semantics and a successful physical attribute probe; it does not eliminate the numerical/compiler trust gap. CPU/CUDA competitiveness is useful context, not the reason for this NO-GO.

A decisive positive mechanism-isolation experiment would have to exercise a distinct lowering rule or proof capability on a case where the closest equally checked manual method cannot meet the same contract/cost. No such rule was identified. Running another N/K sweep would leave that absence unchanged.

**Disposition and bounded follow-up assessment.** The investigated direction stops at **NO-GO**. No research compiler prototype, large experiment campaign, manuscript, paper figure, or journal selection follows from this report.
