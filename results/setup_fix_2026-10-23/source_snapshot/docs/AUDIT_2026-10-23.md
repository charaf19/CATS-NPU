# Repository audit and hardware feasibility — 2026-10-23

## Decision

CATS-NPU is an early research harness with a credible conditional correctness
argument and working CPU controls. It is not yet a validated exact NPU selector
over its declared finite-input domain, and it has no established performance or
novelty contribution. Continue with correctness and feasibility repairs; defer
performance optimization, confirmatory experiments, and manuscript drafting.

The native TopK graph **did compile and execute on the requested NPU**. However,
finite FP16 subnormal inputs produced wrong winners, including an incorrect
`strict_omission_bound` result. FP32 near-tie rankings also failed. Bitonic failed
during host graph construction, before NPU compilation; this is not evidence
that the NPU cannot execute a correctly constructed bitonic graph.

Production Python/C++ code and dependencies were not changed during this audit.
Documentation and diagnostic artifacts were added. All measurements below are
correctness/feasibility diagnostics, not competitive latency measurements.

## Correctness findings, in priority order

### P0: an incorrect NPU result can carry a certificate

`backends.py:191-210` checks that returned values equal the input values at
returned indices. It does not establish that those indices are top-ranked or
that the next candidate is a valid omission bound. The proof explicitly assumes
that property, and actual NPU behavior violates it on a legal finite input.

Reproducer: FP16 `x = (arange(64)-32) * nextafter(float16(0),float16(1))`, K=4,
tile=16. The expected indices are `[63,62,61,60]`. Native hierarchical and
adaptive NPU paths returned `[51,50,49,48]`. The adaptive path reported
`strict_omission_bound`, zero tie repairs, and three rounds. The direct wrapper
returned `[3,2,1,0]`. These are same-FP16-input failures, not FP16-versus-FP32
ranking comparisons. The output-value consistency check did not catch them.

**Established:** incorrect winners/bounds on these subnormal inputs.
**Inference only:** the pattern is consistent with altered subnormal comparison
semantics. Flush-to-zero behavior or a specific compiler defect has not been
isolated, so neither is asserted as the cause.

The raw FP32 one-ULP-at-1 test returned `[0,1,2,3]` instead of `[15,14,13,12]`;
returned values also differed from the supplied FP32 values. This is consistent
with reduced internal precision, but does not isolate which runtime stage
changes precision. FP32 exactness is unsupported by this evidence. The ordinary
wrapper correctly raises for many selected-value disagreements; that guard is
insufficient for wrong rankings with matching selected values.

Required remedy: determine a proven order-preserving device representation or
an explicitly reported exact fallback/rejection policy for unsupported values.
Do not flush scores, loosen comparison tolerances, or silently restrict the
finite-input contract to make tests pass. Any domain change requires an explicit
research decision. Add subnormal, zero, extremal, one-ULP and malicious-backend
counterexamples before using certificates as empirical evidence.

### P0: short final tiles request unprepared OpenVINO K shapes

`algorithms.py:127` caps each initial target at the actual tile length, and
`:69` requests `target+1`. `MethodRunner.prepare()` (`:213-229`) prepares only
the full-tile budget sequence. For N=65, K=10, tile=16, fixed hierarchical
selection prepares K=11 but the last length-one tile requests K=2, raising
`RuntimeError: K=2 not prepared; precompile outside timing` on CPU and NPU.
Adaptive selection with initial budget 3 also misses K=2. Default initial budget
1 happens to prepare it, masking that adaptive case.

NumPy does not enforce prepared-K membership, so existing non-divisible-length
tests pass without covering the OpenVINO invariant. Enumerate every reachable
request for actual tile lengths, or keep a shared fixed request policy, then
test that no kernel is constructed during execution.

### P1: bitonic fails before hardware support is tested

At `backends.py:105-107`, XOR produces a Windows NumPy `intc` array with dtype
character `i` / dtype number 5. It prints as `int32` but OpenVINO constant
construction rejects it. Explicit `astype(np.int32)` produces character `l` /
number 7 and constant construction succeeds in the isolated diagnostic.
Thus “int32 unsupported by the NPU” would be the wrong diagnosis.

A narrow explicit-dtype normalization is the first compatibility repair to
evaluate. It has **not** been applied to production code or used to claim the
whole bitonic network works. After repair, run CPU graph correctness first,
then strict NPU compilation/inference across ties, padding, and numeric edges.

### P1: execution metadata and probe exit status are misleading

Normalize a scalar execution-device string to one list item, retain raw type
and value, and validate the reported requested device where supported
(`backends.py:179`, `probe.py:113`). Also distinguish graph-build, compile,
inference, and numerical failure explicitly; the current `compiled=false` can
mean construction never reached the compiler.

`cli.py:102` only prints a note when `all_passed=false`; the probe returned exit
0 in this audit despite bitonic failure. `02_probe_npu.ps1` consequently cannot
enforce the gate from exit status. Define an explicit required-path criterion
and exit policy; do not require every optional alternative to pass, and do not
treat exit 0 as evidence of feasibility.

## Matrix results and mathematical alignment

`validate_snapshot.py` tested four configurations `(N,K,tile,tile_batch,initial)`:
`(64,4,16,1,1)`, `(65,10,16,2,3)`, `(33,33,16,2,1)`, `(17,1,16,2,1)`.
Each used FP16 and FP32, four methods, and six supplied distributions plus
all-equal, signed-zero, subnormal, and extreme finite inputs. These 320 cases
are a diagnostic collection, not independent statistical trials.

| Method / dtype | Exact matches | Unprepared shape | Value disagreement raised | Wrong returned indices |
|---|---:|---:|---:|---:|
| OpenVINO CPU hierarchical FP16 | 20 | 20 | 0 | 0 |
| NPU direct wrapper FP16 | 37 | 0 | 0 | 3 |
| NPU hierarchical FP16 | 19 | 20 | 0 | 1 |
| NPU adaptive FP16 | 29 | 10 | 0 | 1 |
| OpenVINO CPU hierarchical FP32 | 20 | 20 | 0 | 0 |
| NPU direct wrapper FP32 | 8 | 0 | 32 | 0 |
| NPU hierarchical FP32 | 4 | 4 | 32 | 0 |
| NPU adaptive FP32 | 6 | 2 | 32 | 0 |
| **Total** | **143** | **76** | **96** | **5** |

Raw NPU TopK tie behavior also disagreed with deterministic index order for one
FP16 and one FP32 tied input. Existing host boundary-tie repair is necessary.
An all-equal raw input happened to pass; that does not establish stable ties.

The CPU reference implements descending score / ascending original index,
rejects NaN, either infinity, empty/non-1D arrays, unsupported dtypes, boolean
or nonintegral K, K=0 and K>N. It supports FP16/FP32/FP64. Signed zeros tie by
index. Tile backends support only FP16/FP32. Internal `-inf` padding is excluded
from retained IDs and unused rows are discarded. K=N and K>tile are supported
mathematically, but the OpenVINO short-tile bug prevents some such executions.

The local-K proof and strict `u_j < tau` certificate are valid **conditional
on exact local selection and valid omission bounds on the supplied values**.
Strict comparison conservatively refines equal-score bounds. Completion with
stable boundary repair makes the local-K lemma applicable. Budget doubling
terminates in O(log K) rounds. The implementation follows this structure; the
device counterexample invalidates its prerequisite, not the abstract proof.

The cost of the actual implementation is not simply retained candidates.
With M=ceil(N/W) tiles, initial retained candidates are at most M*r and fixed
local-K retains at most min(N,M*K). Across rounds, backend calls are the sum
of ceil(active tiles per requested K / tile_batch). Each call stages a full
`[tile_batch,W]` matrix and returns requested-K outputs, including bounds and
unused rows. Refinements reread tiles and resend retained prefixes. Host merges
repeat over all current candidates. `np.unique(ids)` and large tie-ID sorts
also prevent treating the reference's entire implementation as an unconditional
O(N)+O(K log K) baseline. Bitonic fully sorts every tile regardless of requested
output budget, so adaptive bitonic does not inherently reduce device sort work.

No explicit fallback for unsupported comparison semantics exists; the current
fallback is boundary-tie repair only. Native C++ and torch wrappers also cast
FP64 to FP32 if called through the Python API; reject that input or implement
its declared precision before calling those paths general exact references.

## Methodological weaknesses to resolve before timing claims

1. **Failure propagation:** analysis reads only observation files. A synthetic
   runtime failure after one successful timed result made `bench` fail, yet
   subsequent `analyze` labeled the remaining row `valid_for_inference=true`.
   Load failures and session completion status into analysis; invalidate
   affected comparisons. Warm-up exceptions currently bypass structured failure
   recording. Preflight mismatches are logged as skips without saved mismatch
   arrays, unlike timed mismatches.
2. **Configuration identity:** case IDs omit initial budget, source version,
   driver/runtime identity, and policy version. These can be pooled incorrectly
   across files. Session IDs are labels, not proof of independent launches;
   duplicate IDs append observations and overwrite manifests. Record immutable
   run IDs, complete configuration hashes, source and environment hashes, and
   reject incompatible or duplicate data. The source has no Git provenance yet.
3. **Ordering and sampling:** method order is shuffled by the same seed for
   every session. Separate order randomization from workload seed, record order,
   and counterbalance sessions. One fixed score vector per case does not sample
   query/input variability. Preserve paired input bytes while varying held-out
   input seeds or actual queries in a declared nested design.
4. **Batch semantics:** `--batch` is tiles per backend call for a single 1D
   score vector. Query batches of 1/8/32 from the master instructions are not
   implemented. Do not report tile batching as multi-query throughput.
5. **Fair baselines:** C++ is unbuilt and PyTorch absent; neither GPU was
   executed. CUDA ties need an exact deterministic method or measured repair.
   All OpenVINO wrappers, including `native_direct`, use host TileSelector
   canonicalization/merge and may repair ties. The raw device graph and the
   application-facing wrapper need distinct labels and latency protocols.
6. **Missing cost counters:** `candidate_count` is final retained size, not
   cumulative returned candidates, transferred bytes, or device work.
   `backend_ns` is host call wall time and includes checks/copies, not isolated
   transfer, synchronization, or hardware kernel time. Add explicit components
   and cumulative counts; account for validation overhead consistently.
7. **Statistical scope:** session-level paired log ratios, cluster bootstrap,
   sign flips, and within-case Holm correction are a useful start. They do not
   establish session independence, latency/P95 uncertainty, workload-level
   generalization, or error control over a large selected case matrix. Freeze
   the comparison family and practical effect threshold before held-out runs.
   Six sessions is a testing resolution floor, not a power justification.
8. **Missing experiments:** no frozen tuning/held-out split, real score
   provenance, allocation-policy ablations, independent sessions, competitive
   datasets, or convincing novel mechanism exist. The pilot configuration is
   descriptive JSON, not read by the CLI. Existing tile choices also differ
   from the master plan (256/1024/4096); test supported shapes before expansion.

## Prior-art status

This is a preliminary source check, not an exhaustive novelty review. No
external speedups are imported as CATS-NPU results. Sources checked 2026-10-23:

| Primary source | What must be distinguished |
|---|---|
| [DeepSelect design](https://github.com/deepseek-ai/DeepSelect/blob/main/docs/DeepSelect-deep-dive.md) | Streaming threshold filtering, randomized block traversal, candidate compaction, and hardware-specific kernels already exist. A threshold plus tiles is insufficient novelty. |
| [TPU-KNN](https://proceedings.neurips.cc/paper_files/paper/2022/hash/639d992f819c2b40387d4d5170b8ffd7-Abstract-Conference.html) and [generalized two-stage work](https://arxiv.org/abs/2506.04165) | Recall-controlled approximate selection must be distinguished from per-input exact certification. Approximation alone is not an exact baseline under this contract. |
| [RadiK](https://arxiv.org/abs/2501.14336) | Scalable GPU radix selection is a relevant strong implementation comparator; target-hardware compatibility and tie semantics still need checking. |
| [RTop-K](https://arxiv.org/abs/2409.00822) | GPU row-wise selection requires a precise algorithm/semantics comparison, not a name-only citation. |
| [Ascend-RaBitQ](https://arxiv.org/abs/2605.16007) | A heterogeneous vector-search system with on-device AI CPU Top-k; distinguish its execution engines and broader quantized search scope from Intel tile selection. |
| [Optimal Aggregation Algorithms for Middleware](https://arxiv.org/abs/cs/0204046) | Threshold reasoning in aggregation is established background; it is not proof that the specific tiled implementation is new or fast. |

[Current OpenVINO NPU documentation](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/npu-device.html)
also qualifies dynamic-shape support by platform/driver. Keep the current static
shape research scope, but do not generalize it to every contemporary NPU.
Pin exact source versions and inspect full algorithms/code before a novelty or
implementation-equivalence claim. No manuscript or venue recommendation follows
from this preliminary check.

|---|---|---|
| 1 | Fix complete-shape preparation, bitonic dtype construction, placement serialization, and probe gate semantics with narrow regression tests | Full suite passes on this Windows environment; tail/initial-budget cases pass; no compilation during inference; raw and normalized device evidence retained |

| 4 | Make the measurement pipeline fail closed and establish comparators | Failure-aware analysis, immutable configuration/source/environment identity, independent order seeds, native C++ correctness and deterministic GPU correctness |
| 5 | Run a small diagnostic pilot | Component/cumulative counters; fixed-vs-adaptive candidate/work/latency comparisons on a declared subset; no confirmatory inference |
| 6 | Design a distinct mechanism and freeze evaluation | Prior-art distinction and correctness/cost derivation; frozen tuning/test split and parameters; feasibility-supported tile/query shapes |
| 7 | Collect held-out independent sessions and ablations | Paired effects and 95% CIs, declared multiplicity family, practical significance, complete failures and negative findings |

**Go:** bounded engineering and hardware validation on the current machine.
**No-go now:** full-domain exact native-NPU claims, FP32 ranking claims,
performance superiority, novelty, or manuscript drafting. If no exact device
representation or useful explicit hybrid path survives validation, revise the
proposed mechanism or stop this direction; do not substitute CPU results for H1.
